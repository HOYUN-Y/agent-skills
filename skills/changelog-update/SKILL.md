# changelog-update — workload 작업 로그 갱신

## 경로 선택 (첫 실행 포함)

- 설치할 때 `install.py --target-root`로 작업 폴더를 저장할 수 있다.
- 실행 요청에 작업 폴더가 있으면 그 경로를 우선한다. 없으면 설치된
  `changelog-update/target-root.txt`를 읽는다. 둘 다 없으면 사용자에게 경로를 묻는다.
- 경로는 실제 존재하는 디렉터리인지 확인하고 실행 전에 사용자에게 표시한다.
- 출력은 항상 `<작업 폴더>/changelog/`, 백업·로그는 `<작업 폴더>/.changelog-backups/`다.
  다른 위치에 기록하려면 그 상위 폴더를 작업 폴더로 지정한다.
- 아래 `<작업 폴더>`와 `<스킬 설치 폴더>`는 설명용 표기다. 명령 실행 전 실제 경로로
  치환하고 공백이 있는 경로는 반드시 인용한다. 설치 위치는 현재 SKILL.md 기준으로 찾는다.
- 최초 실행에 changelog 폴더가 없으면 수동 실행에서 생성한다. 기준 스탬프가 없으면
  전체 파일을 대상으로 삼는다. `.last-run`은 실제 반영·검증 성공 후에만 갱신한다.


`<작업 폴더>/changelog/`는 대상 프로젝트의
**일자별 작업 기록 정본**이다. 이 스킬은 마지막 갱신 이후 늘어난 작업을 읽어
같은 형식으로 이어 쓴다. 폴더 구성(2026-08-21 일별 분리 — 단일 CHANGELOG.md가
850KB까지 자라 매 실행이 전체를 읽고 편집해야 했던 문제의 해소):

- `YYYY-MM-DD.md` — **작업 날짜** 하루치 기록. 이 스킬이 만들고 갱신한다.
- `부가자료.md` — 날짜 없는 상시 섹션(기획·후속계획 / mcp-tracking / 참고자료
  인벤토리 / workload 루트 루스 파일). 매 실행 체크·갱신한다.
- `CHANGELOG.md` — **동결 아카이브** (기존 기록이 있을 때만 존재). 읽기는 되지만
  🚨 **절대 수정하지 않는다.** cron-run.sh가 md5로 감시하며 바뀌면 그날 실행을
  실패 처리한다. 과거 맥락이 필요할 때 참조만 한다.
- `.last-run` — 게이트 스탬프. 무인은 cron-run.sh가, 수동은 반영·검증 성공 후 실행 시작 시각으로 갱신한다.

> 이 문서는 도구 무관 순수 절차서다. Claude Code / Codex / Cursor 어디서든
> 이 파일을 읽고 그대로 수행할 수 있다.

## 언제 쓰나 (트리거)

- "changelog 갱신해줘" / "오늘 작업 정리해줘" / "0724 폴더 반영해줘"
- 선택적으로 등록한 스케줄러의 무인 실행 (`scripts/cron-run.sh`)
- 하루 작업을 마치고 기록을 남기고 싶을 때

## 사전 조건

- 작업 폴더: 실행 인자 또는 설치 시 저장한 경로
- 대상: `changelog/` 폴더 (일별 `YYYY-MM-DD.md` + `부가자료.md`)
- 작업 폴더의 Git 사용 여부와 관계없이 편집 전 백업이 필수다.

폴더명별 반영 위치와 프로젝트 예시는 기존 운영 사례다. 다른 작업 폴더에서는 실제 구조와
문서 근거에 맞게 분류하고, 예시에 나온 폴더나 수치를 새로 만들지 않는다.

## 절대 하지 말 것

**이 스킬의 쓰기 권한은 `changelog/` 안의 일별 파일과 `부가자료.md`뿐이다.**
그 밖의 모든 부수효과는 요청받지 않은 것이며, 매일 22:00 무인으로 돌기 때문에
아무도 보고 있지 않다. 아래는 예외 없다. 사용자가 그 자리에 없으므로
"괜찮겠지" 판단을 하지 않는다.

### 파일 쓰기

- 🚨 **`changelog/` 폴더 밖의 어떤 파일도 만들거나 고치거나 지우지 말 것.**
  열람한 파일을 "고치는 김에" 정리·수정하지 않는다. 오타·깨진 링크·낡은 내용을
  발견해도 **changelog에 기록만 하고 원본은 건드리지 않는다.**
- 🚨 **`changelog/CHANGELOG.md`(동결 아카이브)를 수정하지 말 것.** 같은 폴더 안에
  있어 도구 규칙이 막아주지 못한다 — cron-run.sh의 md5 검사가 잡아 그날 실행을
  실패 처리한다. 읽기·참조만 한다.
- 🚨 **기존 기록을 삭제하거나 다시 쓰지 말 것.** 추가·보강만 한다.
  문장을 "정리"하겠다고 기존 항목을 재작성하지 않는다. 과거 기록은 그때의 판단을
  담고 있어 값이 있다. (cron-run.sh가 파일별 크기 감소를 실패로 잡는다.)

### 비밀값

- 🚨 **`.env`·API 키·토큰·비밀번호·인증서·계정 자격증명을 열람하지 말 것.**
  `changed-files.sh`가 확실한 확장자는 목록에서 빼지만 **완전하지 않다.**
  작업 폴더에 자격증명이 있을 수 있다. 파일을 열었는데 비밀값이 보이면 **즉시 읽기를 멈추고 넘어간다.**
- 🚨 **비밀값을 CHANGELOG에 옮겨 적지 말 것.** 값의 일부·마스킹한 형태·"참고용" 발췌
  전부 금지다. CHANGELOG는 평문이고, 백업 30벌로 복제되며, 주간 근무일지로도 흘러간다.
  필요하면 **존재만** 기록한다: "API 키 로테이션 작업(값 미기재)".
- 🚨 **비밀값을 복사·이동·업로드·외부 전송하지 말 것.**

### git · 배포

- 🚨 **git 쓰기 작업을 하지 말 것** — `commit` · `push` · `merge` · `rebase` · `reset` ·
  `checkout`(브랜치 전환) · `gh pr create` · `gh pr merge` 전부. 조회(`log`·`status`·`diff`)만 허용.
- 🚨 **배포하지 말 것** — `wrangler deploy` · `npm publish` · GitHub Actions 트리거 ·
  마이그레이션 적용. 저장소(`<관련 저장소>`) 코드·DB·배포는 범위 밖이다.
- 🚨 **운영 DB에 쓰지 말 것.** 이 스킬은 DB를 조회할 이유 자체가 없다.
- 🚨 **외부로 아무것도 보내지 말 것** — 업로드·API 호출·메시지 발송. 로컬 파일만 읽고 쓴다.

### 서술

- 🚨 **`mcp-tracking/` 관련 내용에 사용자 이메일·user_id를 쓰지 말 것.**
  해당 폴더 `AGENTS.md` 규칙이며 CHANGELOG는 그 폴더 밖이다. 익명화된 패턴만 적는다.
  (예: "내부 테스트 계정 2개가 전체 호출의 약 60%" — 계정 주소는 쓰지 않는다.)
- 추측으로 쓰지 말 것. 파일에 없는 결과·수치를 지어내지 않는다. → **판단 규칙** 절 참조.

> 위 금지에 걸리는 작업이 정말 필요해 보이면 **하지 말고 CHANGELOG에 "확인 필요"로 남긴다.**
> 무인 실행에서는 되물을 수 없고, 되물을 수 없으면 하지 않는 쪽이 맞다.

## 절차

### 1. 대상 파일 판별

```bash
"<스킬 설치 폴더>/changelog-update/scripts/changed-files.sh" "<작업 폴더>"
```

마지막 성공 실행(`changelog/.last-run` 스탬프)보다 mtime이 최신인 파일을 출력한다
(노이즈 제외는 스크립트 주석 참조). 스탬프는 성공한 실행만 전진시키므로, 실패한 날의
대상은 다음 실행이 다시 잡는다.
**출력이 비어 있으면 갱신할 것이 없다. 아무것도 하지 말고 종료한다.** 실패가 아니다.

### 🚨 아무것도 쓰지 않고 끝낼 때는 반드시 표식을 남긴다

`cron-run.sh`는 **changelog/ 폴더의 상태 지문(파일 목록+md5)이 바뀌었는지로만** 성공을 판정한다. 그래서
"쓸 게 없어서 안 썼다"와 "써야 하는데 못 썼다"가 구분되지 않는다 —
2026-08-13 실행이 실제로 그랬다(대상 1건이 이미 기록된 내용이라 정상적으로 건너뛰었는데
`FAILED-2026-08-13.md`와 macOS 알림이 나갔다. 08-12의 진짜 실패와 같은 모양으로 남았다).

그러니 **changelog/ 안의 어떤 파일도 고치지 않고 끝내기로 했다면, 마지막 출력에 아래 한 줄을
정확히 그대로 넣는다.**

```
NO_CHANGE_NEEDED: <한 줄 사유>
```

예)
```
NO_CHANGE_NEEDED: 대상 1건(skill/…/check-detail.sh)이 mtime만 갱신됐고 내용은 이미 2026-08-13.md에 반영돼 있음
```

- 이 표식은 **실제로 아무것도 안 썼을 때만** 쓴다. 한 글자라도 고쳤으면 쓰지 않는다.
- **판단이 서지 않아서 못 쓴 것은 여기 해당하지 않는다.** 그건 미완이고,
  "미독 — 다음 실행에서 반영 필요"로 해당 일별 파일에 적어야 한다(→ 서술 규약).
- 표식이 없는데 상태 지문도 그대로면 `cron-run.sh`는 **실패로 처리한다.** 그게 맞다.

### 2. 백업

🚨 **무인 실행이면 이 단계를 통째로 건너뛴다. 백업을 시도하지 말고 3단계로 간다.**

`mkdir`·`cp`는 `--allowedTools`에 **없다.** 무인 실행에서 이걸 부르면 승인 프롬프트가 뜨는데
답할 사람이 없어 **그 자리에서 실행이 끝난다** — 88건을 앞에 두고 CHANGELOG를 한 글자도
못 고친 채 죽는다(2026-08-12 22:00 실행이 실제로 그랬다. 31초 만에 "승인이 필요한
명령입니다. 진행해도 될까요?"를 남기고 종료, `FAILED-2026-08-12.md`).
**백업은 `cron-run.sh`가 claude를 띄우기 전에 이미 떴다.** 네가 할 일이 아니다.
"혹시 모르니 한 번 더" 백업하려는 충동이 이 스킬을 죽이는 경로다.

무인 여부 판별은 아래 "무인 실행 모드" 절을 따른다. **판단이 안 서면 건너뛴다** —
백업을 건너뛴 대가는 `cron-run.sh` 백업과 중복되지 않는 것뿐이고,
시도한 대가는 그날 갱신 전체가 날아가는 것이다.

수동 실행일 때만 (폴더째 뜬다 — 이번 실행이 일별 파일 여러 개와 부가자료를 함께 고칠 수 있다):

```bash
cd "<작업 폴더>"
mkdir -p .changelog-backups
cp -R changelog ".changelog-backups/changelog-$(date '+%Y%m%d-%H%M%S')"
```

### 3. 파일 읽고 작업 파악

각 파일을 읽고 **무엇을 했고, 무엇이 확인됐고, 무엇이 남았는지** 파악한다.

- 문서(`.md`·`.txt`)는 통독한다. 결론뿐 아니라 근거·수치·미해결 항목까지 본다.
  🚨 **크기는 생략 사유가 아니다.** 60KB짜리 `.md`도 `offset`·`limit`으로 나눠 읽어 전량
  반영한다. 먼저 `grep -n "^#"`로 목차를 뽑고 절 단위로 끊어 읽으면 컨텍스트가 넘치지 않는다.
  (2026-08-13 실패: `2026-08-12_후속코드개선.md` 60,177바이트를 "통독하지 않아 확인 필요"로
  넘겼는데, 나중에 나눠 읽었더니 **429 일괄 throw·저층 기준 오해석 지적·103만 행 rows read**
  같은 그날의 핵심이 거기 있었다. 요약본만 읽고 상세본을 건너뛴 것이 원인이다.)
- **데이터 파일(`.csv`·`.json`·`.ipynb`·`.xlsx`)은 통독하지 않는다.** 헤더·행 수·표본 몇 줄만
  확인해 "무엇을 담은 산출물인지"만 파악한다. 통독하면 컨텍스트가 넘친다.
- 파일이 많으면 폴더 단위로 묶어 읽는다. 한 폴더가 하나의 작업 단위인 경우가 많다.
  🚨 단, **"묶어 읽는다"는 "묶어서 한 줄로 적는다"가 아니다.** → 서술 규약의 「파일 목록은
  기록이 아니다」 참조.
- **회차별 문서(`result.md`·`result2.md`·`result4.md`, `*testSequence*/`, `1차`·`2차`)는 회차마다
  따로 읽고 따로 적는다.** 결과가 같아도 호출 수·소요시간·판정이 다르면 그 차이가 기록의
  핵심이다(2026-08-12 같은 조사 3회가 7.7초 / 4회 12.8초 / 31.1초로 갈렸고, 이 차이가
  "동일 성공 요청 재호출 금지" 규칙의 근거가 됐다).
- **"제작 과정"·"진행 기록"·"작업 로그" 류 문서는 결과 절보다 실패 절을 먼저 본다.**
  실패·재시도 표, 결론 변천 표, 뒤집힌 가정 목록이 그 문서에서 가장 값진 부분이고
  가장 잘 누락된다.

### 4. 반영 위치 결정

| 변경 위치 | 반영할 곳 |
| --- | --- |
| `workload_YYMMDD/` · `workload-YYMMDD/` | **그 작업 날짜의** `changelog/YYYY-MM-DD.md` |
| `plan/` · `후속계획/` · `db-increment/` · `result/` | `changelog/부가자료.md` — 기획·후속계획 |
| `mcp-tracking/` | `changelog/부가자료.md` — mcp-tracking (기존 항목 갱신, 새 섹션 신설 금지) |
| `manual/` · `reference/` · `api_documents/` | `changelog/부가자료.md` — 참고자료 인벤토리 |
| `workload/` 루트 루스 파일 | `changelog/부가자료.md` — workload/ 최상단 루스 파일 |

- **파일명은 작업 날짜다, 실행 날짜가 아니다.** 폴더명(`workload-260819` → `2026-08-19.md`)과
  파일 내용으로 작업 날짜를 판별한다. 밀린 실행이면 한 번에 여러 날짜 파일을 만드는 게 정상이다.
- 해당 날짜 파일이 **이미 있으면 그 파일에 이어 쓴다.** 항목을 재작성하지 않는다.
  (같은 날 오전에 쓰고 오후에 파일이 더 생기는 일이 잦다.)
- 날짜 파일이 없으면 **새로 만든다.** 형식:

  ```markdown
  # 2026-08-21

  > 갱신 이력: 2026-08-21 22:0x 자동(무인) — workload-260821/ 반영
  ```

  첫 줄은 `# YYYY-MM-DD` 제목, 그 아래 인용 블록에 갱신 이력을 쌓는다.
  본문은 기존 CHANGELOG의 날짜 항목과 같은 형식(4블록 구조)이다.
- 하루 안에서 시점이 뚜렷이 갈리면 별도 굵은 소제목 블록으로 구분한다.
  (기존 예: `**배포 후 재검증(같은 날 후속, ...)**`, `**오후~저녁 후속(기획·조사, 코드 미착수)**`)
- **`부가자료.md`는 매 실행 반드시 한 번 체크한다** — 대상 파일 중 위 표의 부가 자료
  경로에 해당하는 것이 있으면 해당 절을 갱신하고, 없으면 건드리지 않는다.
- 과거 형식이 궁금하면 아카이브(`changelog/CHANGELOG.md`)의 해당 절을 **읽어서** 참고한다.
  850KB이므로 통독하지 말고 `grep -n`으로 필요한 절만 찾아 읽는다.
- 🚨 **전환기 중복 방지**: 새 날짜 파일을 만들기 전에 아카이브에 같은 날짜 절이 있는지
  `grep -n "^### YYYY-MM-DD"`로 확인한다. 있으면(수기 기록 등) 그 내용을 일별 파일로
  옮기지 말고 — 아카이브는 불가침이다 — **아카이브에 없는 내용만** 일별 파일에 쓰고,
  파일 상단 인용 블록에 "YYYY-MM-DD 이전 기록은 아카이브 해당 절 참조"를 남긴다.

### 5. 항목 작성 — 4블록 구조

일자별 항목은 아래 네 갈래를 유지한다. 해당 없으면 생략한다.
**각 갈래는 최대한 자세히 쓴다** — 기준은 아래 **서술 규약** 절을 그대로 따른다.

```
- 핵심 작업: 무엇을 만들었나·고쳤나. PR 번호·브랜치명·파일경로·도구명을 함께.
- 결정/이슈: 무엇을 왜 그렇게 정했나. 번복·보류·범위 제외도 포함.
- 테스트/검증 결과: 통과·실패를 수치로. 무엇이 확인됐고 무엇이 재현됐나.
- 미해결/다음 액션: 남은 것. 누구 승인 대기인지, 왜 미뤘는지까지.
```

### 6. 검증 후 보고

- 고친 일별 파일이 실제로 바뀌었는지 확인한다(백업과 `diff`, 무인이면 Read로 재확인).
- 각 일별 파일 상단 인용 블록에 이번 갱신을 한 줄 남긴다: 날짜 + 반영 범위 + 자동/수동 여부.
- 사용자에게는 **무엇을 반영했고 무엇을 판단 보류했는지** 보고한다.

## 서술 규약 — "자세히"의 기준

🚨 **기본값은 "최대한 자세히"다.** 짧게 쓰라는 지시가 없는 한 항상 최대 상세로 쓴다.
읽은 파일에서 확인된 사실은 **하나도 빠뜨리지 말고** 옮긴다. 요약·압축·생략은
명시적으로 요청받았을 때만 한다. 분량이 길어지는 것은 이 스킬에서 결함이 아니라
정상이며, **짧게 쓴 것이 결함이다.**

단, **"자세히"는 "많이 쓰는 것"이 아니라 "확인된 것을 빠짐없이 쓰는 것"이다.**
분량을 채우려고 추정·짐작으로 빈칸을 메우는 것은 금지다 — **판단 규칙** 절이
이 절보다 우선한다. 근거가 없으면 분량이 짧아지는 게 맞다.

이 CHANGELOG는 요약이 아니라 **나중에 근거를 되짚을 수 있는 기록**이다.
아래를 항상 남긴다. 이게 빠지면 자세히 쓴 게 아니다.

- **수치는 원본 그대로.** "빨라짐" ❌ → "평균 23.875초→9.437초, P50 24.750→7.980" ⭕
- **식별자를 남긴다.** PR 번호(`PR #92`), 브랜치명(`fix/molit-call-guards`),
  도구명(`get_complex_trades`), 테이블·필드명(`kapt_trade_match`), 파일 경로.
- **테스트 결과는 규모까지.** "테스트 통과" ❌ → "typecheck·test 59 files/564 tests·build 통과" ⭕
- **결정에는 이유를.** "A로 정함" ❌ → "A로 정함 — B는 정액 과금 정책과 충돌해서" ⭕
- **부정 결과도 기록한다.** 재현 실패, 백로그 강등, 범위 제외, 번복된 결정은
  성공만큼 중요하다. 나중에 같은 길을 두 번 가지 않게 해준다.
- **미해결은 상태까지.** "미완" ❌ → "코드 머지만 완료, 운영 Worker 실배포·원격 재검증 미수행" ⭕
- **작업 단위를 뭉뚱그리지 않는다.** 파일 5개가 각각 다른 작업이면 항목도 5개다.
  "여러 CSV 검토" ❌ → 파일별로 무엇을 몇 건 검토해 어떤 결론이 났는지 각각 ⭕
- **중간 과정도 남긴다.** 최종 결과만이 아니라 몇 차에 걸쳐 어떻게 바뀌었는지
  (1차 시도 → 실패 원인 → 2차 반영)를 순서대로 적는다.
- 길이는 제한하지 않는다. 한 날짜에 작업이 많으면 항목이 길어지는 게 맞다.
  **분량을 아끼려고 사실을 버리지 않는다.** 컨텍스트가 부족하면 줄여 쓰지 말고
  파일을 나눠 읽어 전부 반영한다.

#### 🚨 파일 목록은 기록이 아니다

폴더 안에 무엇이 **있는지** 적는 것은 기록이 아니다. 그 파일들로 무엇을 **했고 무엇이
나왔는지**를 적어야 기록이다. `ls` 결과를 문장으로 옮기는 순간 그 항목은 실패한다.

```
❌ `test-results/`(3파일): 보고서·결과 JSON·제작 스크립트.
⭕ `test-results/`: 응답시간 비교 시험 3회, 평균 12초→8초. 1차 실패 원인은
   의존 도구 미설치로 기록됨. 2차 설치 후 재시험 통과, 운영 재검증 미수행.
```

판별법 — 다음이 **하나도 없으면** 파일 목록을 적은 것이다: 수치 · 시각 · 식별자 ·
판정 결과 · 실패 내용 · 그래서 무엇이 달라졌는지.

파일이 많은 폴더는 **파일 개수를 적고 끝내지 말고**, 그 폴더가 답한 질문 하나와
그 답의 근거 수치를 적는다. 개수는 부수 정보다.

#### 🚨 "확인 필요"는 근거가 없을 때만 쓴다

`판단 규칙`의 "확인 필요"는 **원본에 근거가 없을 때** 쓰는 표시다.
**내가 읽지 않은 파일에는 쓸 수 없다.** 읽으면 알 수 있는 것을 "확인 필요"로 적는 것은
판단 보류가 아니라 **작업 미완을 보류처럼 위장하는 것**이다.

- 파일이 존재하고 읽을 수 있다 → **읽는다.** 크면 나눠 읽는다.
- 원본에 그 수치·결론이 아예 없다 → "확인 필요" ⭕
- 시간·컨텍스트가 부족하다 → "확인 필요" ❌ → 나눠 읽거나, 못 읽었다고 **그대로** 보고한다.

무인 실행에서 진짜로 읽지 못했다면 "확인 필요"가 아니라
**"미독 — 다음 실행에서 반영 필요(파일 경로·크기 명시)"**로 적어 다음 실행이 집어가게 한다.

### "최대한 자세히"가 양보하는 유일한 지점

**절대 하지 말 것**과 **판단 규칙**이 서술 규약보다 우선한다. 자세히 쓰려고
아래를 넘지 않는다 — 상세함보다 안전과 정확이 먼저다.

- 비밀값은 아무리 상세히 쓰고 싶어도 **존재만** 적는다(값·일부·마스킹 전부 금지).
- `mcp-tracking/` 관련은 이메일·user_id 없이 익명 패턴으로만 적는다.
- 근거 없는 상세는 상세가 아니라 창작이다. 파일에 없으면 **쓰지 않거나** 등급을 붙인다.
- 큰 데이터 파일은 여전히 통독하지 않는다(지뢰 ⑤). 대신 헤더·행 수·열 구성·표본을
  **구체적으로** 적어 상세함을 확보한다: "CSV 40건, 열 12개(apt_seq·단지명·...)" ⭕

## 판단 규칙 — 근거 등급

🚨 **추정 금지. 파일에 적힌 것만 쓴다.** 이건 "최대한 자세히"보다 **상위 규칙**이다.
상세하게 쓰려다 빈칸을 메우고 싶어지는 순간이 가장 위험하다. 빈칸은 **빈칸으로 남긴다.**

- 파일에 없는 **수치·건수·비율·소요시간·성공률**을 지어내지 않는다. 어림수도 금지다.
- 실행하지 않은 명령의 **결과를 상상해 쓰지 않는다.** 로그가 없으면 결과도 없다.
- 코드·설정을 읽고 **"그러니 이렇게 동작했을 것"이라고 쓰지 않는다.**
  동작은 실행 기록으로만 확인된다.
- 파일명·폴더명만 보고 **내용을 유추해 쓰지 않는다.** 열어서 확인하거나, 안 쓴다.
- 여러 파일을 읽고 **인과관계를 임의로 연결하지 않는다.**
  ("A 다음 B가 생겼으니 A 때문에 B" ❌ — 문서에 그렇게 적혀 있을 때만 쓴다.)
- 판단이 서지 않으면 **"내용 확인 필요"로 남기고 넘어간다.** 특히 무인 실행에서는
  되물을 수 없으므로, 모르는 것을 채워 넣는 대신 모른다고 적는 쪽이 항상 맞다.

| 등급 | 근거 | 쓰는 법 |
| --- | --- | --- |
| A | 로그·테스트 출력·산출물 파일에 수치가 그대로 있음 | 단정해서 쓴다 |
| B | 문서에 저자가 결론으로 적었으나 원본 출력은 없음 | "…로 기록됨" |
| C | 파일 존재·이름만으로 추론 | "…로 보임" 또는 쓰지 않는다 |

**A가 아닌 것을 A처럼 쓰지 않는다.** 등급을 낮춰 적는 것은 상세함의 손실이 아니라
정확도의 확보다. B·C를 A처럼 단정하는 것이 이 스킬에서 가장 큰 결함이다.

### 금지 문장 패턴

- "배포 완료" — 머지와 배포는 다르다. 파일에 배포 확인 근거가 없으면 "머지만 확인됨"으로.
- "테스트 전부 통과" — 개수가 없으면 "통과로 기록됨".
- "성능이 개선됐다" — 전/후 수치가 없으면 쓰지 않는다.
- 계획 문서를 읽고 "구현했다"라고 쓰는 것. **계획과 구현은 다르다.**
  계획만 있으면 "계획 수립(구현 미착수)"으로 명시한다.

## 무인 실행 모드 (launchd)

`사용자가 등록한 스케줄러`가 원하는 시간에
`scripts/cron-run.sh`를 실행한다. 스크립트가 하는 일:

1. `changed-files.sh`로 게이트 — 변경 없으면 claude를 띄우지 않고 종료
2. `changelog/` 폴더째 타임스탬프 백업 (최근 30개 유지)
3. `claude -p "/changelog-update"` 실행 (워치독 3시간 — 초과하면 kill)
4. **상태 지문(파일 목록+md5) 비교로 실제 변경 확인** — 종료코드만 믿지 않는다.
   아카이브 수정·기존 파일 축소도 여기서 실패로 잡는다
5. 성공 시 `changelog/.last-run` 스탬프를 실행 시작 시각으로 전진
6. 실패 시 `.changelog-backups/FAILED-<날짜>.md` + macOS 알림

무인 모드에서는 사용자에게 되물을 수 없다. **판단이 서지 않는 파일은 추측해서 쓰지 말고
해당 항목을 "내용 확인 필요"로 남기고 넘어간다.**

**지금 이 실행이 무인인지 아는 법**: `cron-{오늘날짜}.log`의 마지막 `=== ... 시작` 줄에
`[무인 launchd]` 표시가 있고 그 뒤로 종료 줄이 없으면 **그게 지금 실행 중인 자기 자신이다.**
`claude -p`는 최종 텍스트를 종료 시점에 한 번만 stdout으로 내보내므로, 실행 중에 로그를
읽으면 자기 출력은 아직 없는 게 정상이다. → 지뢰 ⑥

```bash
"<스킬 설치 폴더>/changelog-update/scripts/cron-run.sh" "<작업 폴더>"   # 수동 재실행
launchctl list | grep changelog-update                  # 등록 확인
```

## 지뢰 목록 — 같은 실수 반복 금지

1. **오전에 쓴 항목이 오후 작업으로 낡는다.** 2026-07-23이 실제로 그랬다(13:11 작성 →
   15:00~19:01 파일 추가). 날짜 항목이 이미 있어도 **반드시 갱신 여부를 확인**할 것.
2. **`mtime` 기준이라 파일을 열어보기만 해도 잡히는 경우가 있다.** 내용이 실제로
   달라졌는지 보고, 변경이 없으면 changelog를 건드리지 않는다. (기준선이 파일
   mtime이던 시절에는 진단 중 `touch` 한 번으로 기준선이 통째로 밀리는 사고도
   있었다 — 2026-08-21. 스탬프 방식은 그 부작용이 없지만, 대상 판별이 mtime인
   것은 여전하다.)
3. **계획서를 구현으로 착각하지 말 것.** `mcp-evol/`·`plan/`은 계획 문서다.
   실제 구현은 저장소 PR과 테스트 결과로만 확인된다.
4. **mcp-tracking은 매일 파일이 생긴다.** 리포트 이력 줄을 압축해서 갱신할 뿐,
   날마다 새 항목을 만들지 않는다.
5. **큰 CSV를 통독하면 컨텍스트가 넘쳐 갱신 자체가 실패한다.** 표본만 본다.
6. **자기 자신을 "수동 실행"으로 오진하지 말 것.** 2026-07-27 22:00 무인 실행이 실제로
   그랬다 — 로그에 자기가 남긴 `시작`·`백업` 줄만 보이자 "22:00 무인 실행은 백업까지만
   남기고 로그가 끊김, 이건 수동 실행"이라고 CHANGELOG에 적었다(그 무인 실행이 본인).
   판별법은 "무인 실행 모드" 절 참조. 확신이 안 서면 **무인/수동을 아예 쓰지 않는다.**
   `cp`·`git` 같은 명령이 거부되면 그건 "샌드박스"가 아니라 무인 `--allowedTools` 제한이다.
